릴리즈 검증 프로세스 개선 제안 — 가설에서 재정의까지

중간점검(빌드 검증) 이후에도 개발이 계속 진행되면서, 이미 수정·검증했던 이슈가 재발하는 문제를 발견했습니다. 처음엔 "검증 상태를 보호할 별도 브랜치가 필요하다"고 판단해 제안을 준비했지만, 리드와의 면담을 거치며 문제 자체를 다시 정의하게 된 과정을 기록했습니다.

역할개발 PM
방식가설 수립 → 이해관계자 면담 → 재정의
상태면담 후 재정의 완료, 후속 단계 적용 예정

1. 문제 상황

검증했던 이슈가 다시 발생했다

중간점검을 운영하던 중, 이미 확인·수정했던 이슈가 이후 빌드에서 재발하는 사례가 반복적으로 확인됐습니다. Dev 브랜치는 개발 중인 작업이 계속 반영되는 구조라, 중간점검을 위해 검증이 끝난 이후에도 새로운 변경사항이 들어갈 수 있었습니다.

"방금 테스트 했는데, 스킵하면 연출이 정상적으로 안 나옵니다"
"어제 그랬는데... 오늘 잘 나오다가 또 저러네요"

같은 현상이 정상 → 비정상 → 정상으로 반복되면서, "이미 검증한 상태"라는 개념 자체가 불안정하다는 걸 확인했습니다. 핵심 질문은 이거였습니다 — Dev 브랜치에서 개발을 계속 진행하면서도, 중간점검에서 검증한 상태를 어떻게 안정적으로 유지할 것인가?

2. 초기 가설과 제안

"검증 상태를 보호하는 안정화 브랜치가 필요하다"

문제를 분석하면서 네 가지 대안(현행 유지 / 부분적 변경 통제 / 중간점검 안정화 브랜치 / Feature 단위 브랜치)을 비교했고, 중간점검 시점에 검증 대상 상태를 별도 브랜치로 분기해 안정화하는 방식이 가장 유력하다고 판단했습니다. 제안을 준비하며 "현재 방식의 재작업 비용 vs 브랜치 관리 공수"를 비교할 확인 항목까지 정리했습니다.

※ 개념 목업 — 초기 제안 당시 구상했던 구조

3. 리드 면담 — 가장 중요한 발견

중간점검의 목적 자체가 달랐다

면담 전 중간점검은 특정 시점의 안정화된 상태를 기준으로 검증해야 한다고 전제하고 있었습니다.
면담 후 리드의 설명에 따르면 중간점검의 실제 목적은 완성 상태를 고정해 검증하는 것이 아니라, 개발 진행도를 확인하고 빠진 요소를 발견하는 Progress Check였습니다. 개발이 진행 중이므로 어제 정상이던 것이 오늘 다시 깨지는 현상 자체는 현재 단계에서 감수하고 있으며, 긴급 Block 이슈만 우선 대응하고 나머지는 다음 단계로 넘기는 방식으로 이미 운영되고 있었습니다.
판단 현재 프로젝트 단계에서 별도 안정화 브랜치를 관리하는 공수는 중간점검의 목적 대비 과하다는 리드의 판단을 수용했습니다. 대신 브랜치 전략은 실제 마감(리소스 마감, 개발 마감) 단계에서 다시 설계하기로 논의를 이동했습니다.

4. 재정의된 문제

"브랜치 여부"가 아니라 "판단 기준"의 문제였다

면담을 통해 문제를 다시 정의했습니다. 중간점검과 마감 검증은 목적이 다른 두 단계이므로 같은 운영 기준을 적용하면 안 되고, 이슈 대응 판단의 주체가 존재하더라도 이슈 유형별 판단 범위와 R&R이 명시적으로 정리되어 있지 않으면 PM이 판단을 과도하게 떠안거나 판단 요청이 지연될 수 있다는 게 더 근본적인 문제였습니다.

※ 개념 목업 — 면담 후 재정의한 문제 구조

5. 배운 점

문제를 해결하기 전에 그 프로세스의 실제 목적을 먼저 확인해야 한다는 걸 다시 확인했습니다. "불안정성을 모두 없애는 것"이 항상 정답은 아니었습니다 — 중간점검의 목적이 완성도 검증이 아니라 진행도 확인이라면, 불안정성을 감수하되 Block 이슈만 우선 대응하는 게 현재 단계엔 더 적합했습니다. 제 제안이 틀렸다고 방어하기보다, 실제 운영 의도를 먼저 확인하고 제안을 수정하는 과정 자체가 이번 작업에서 가장 중요한 부분이었습니다.
