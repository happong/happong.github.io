# Dev Build 중간점검 운영 프로세스 개선

> 상태: 진행 중
> 시작일: 2026-09-10

## 1. 문제 상황

개발 초창기 단계에서 Dev Build에 지속적으로 개발 내용이 반영되고 있으며, 일정 지연과 품질 이슈에 대응하기 위해 주간 중간점검 빌드를 운영하고 있다.

기존 운영에서는 다음 문제가 반복되었다.

- 중간점검에서 무엇을 반드시 확인하고 무엇을 다음 단계로 넘길지 명확한 범위가 부족함
- 빌드 완료 이후에도 수정 요청과 추가 빌드가 이어짐
- 실제 대응이 필요한 인원과 대기할 필요가 없는 인원이 명확하게 구분되지 않음
- PM이 빌드를 직접 확인하고 이슈를 찾으면서 각 팀의 QA/판단 업무까지 일부 담당하는 구조가 발생함
- 당일 대응 여부와 업무 종료를 누가 최종 결정하는지 명확하지 않음

## 2. 문제 정의

단순히 '야근이 많다'가 핵심 문제라기보다 다음과 같이 정의했다.

> 중간점검 빌드의 검증 범위, 이슈 대응 기준, 종료 기준 및 의사결정 주체가 명확하지 않아 반복적인 수정/빌드 대응과 불필요한 대기 인원이 발생한다.

## 3. 최초 제안: Check Scope Freeze

개발 자체를 중단하는 것이 아니라 **중간점검에서 반드시 확인할 범위만 사전에 정의**하는 방식으로 제안했다.

### 운영 개념

`계획 → 마감 → 안정화 → 검증`

확인 질문:
1. 이번 주까지 하기로 한 내용이 실제로 반영되었는가?
2. 반영된 내용이 최소한 동작하는가?
3. 문제가 있다면 다음 단계까지 해결 가능한가?

### 이슈 분류
- **Block**: 당일 대응이 필요한 진행 불가/검증 불가 수준의 이슈
- **Development**: 개발 진행 중이거나 추가 개발이 필요한 이슈
- **Polishing**: UI, 연출, 수치, 표현 등 즉시 대응이 필수는 아닌 개선사항

## 4. 팀장 협의 결과

팀장 의견은 계획 → 마감 → 안정화 → 검증 단계가 필요하지만 프로젝트 초창기이고 매주 밀어넣기가 바쁘므로 순차적으로 적용할 필요가 있다는 것이었다.

우선 빌드 일정부터 명확하게 고정하여 운영하기로 했다.

### 빌드 일정

수요일:
- 03:00
- 11:00
- 15:00
- 18:00
- 추가 요청 시 추가 빌드

목요일:
- 03:00
- 11:00

## 5. 실제 운영에서 발견된 추가 문제

빌드 일정은 공지되었으나 **빌드 마감**과 **업무 대응 마감**의 의미가 명확하게 합의되지 않았다.

PM은 18시 빌드를 수요일 마무리 빌드로 이해했으나, 팀장 측에서는 18시 이후에도 22시까지 빌드 이슈 대응이 필요한 것으로 인식하고 있었다.

이를 통해 다음 문제가 추가로 확인되었다.

- 18시 빌드가 업무 종료를 의미하는지 불명확함
- 22시까지 전원이 대기하는 운영이 반복됨
- 22시 이후 누가 잔류 인원을 결정할지 명확하지 않음
- PM이 최종적으로 업무를 마무리 판단하는 상황이 발생할 수 있음
- PM팀이 빌드 상태를 직접 확인하면서 QA 역할과 PM 역할의 경계가 모호함

## 6. 개선 방향: R&R과 의사결정 분리

### PM팀
- 빌드 일정 관리
- 각 팀장에게 빌드 확인 요청
- 각 팀에서 전달한 이슈 및 대응 현황 취합
- 전체 현황 공유
- 팀장/AD의 결정사항에 따라 대기 인원 안내 및 대기 해제

**PM팀에서 빌드를 직접 QA하는 역할은 제거한다.**

### 각 팀장
- 담당 영역 빌드 확인
- 자기 팀 이슈 확인
- 수정 필요 여부 판단
- 수정 담당자 지정
- 수정 완료 여부 확인

### 팀장/AD
- 당일 대응 필요 여부 최종 판단
- 당일 대기 인원 최종 결정
- 업무 종료/추가 대응 여부 결정

## 7. 현재 제안 중인 운영안

### 빌드 일정
- 03:00
- 15:00
- 18:00
- 20:00
- 21:00
- 22:00 이후 전원 대기 해제 여부 판단

### 15시 / 18시 / 21시 확인

PM이 각 팀장에게 담당 영역 확인을 요청한다.

각 팀은 다음 정보를 전달한다.
- 수정 필요사항
- 담당 팀
- 담당자
- 수정 필요 여부
- 수정 완료 여부
- 당일 대응 필요 여부

PM은 전달받은 내용을 전체 리스트로 취합한다.

### 22시 이후

PM이 임의로 잔류 인원을 결정하지 않고 **팀장/AD가 당일 추가 대응이 필요한 인원과 종료 여부를 최종 결정**한다.

PM은 결정된 내용을 전달하고 그 외 인원은 대기 해제한다.

## 8. 핵심 R&R

`PM → 확인 요청 / 취합 / 공유 / 운영`

`각 팀장 → 담당 영역 확인 / 이슈 판단 / 담당자 지정`

`팀장·AD → 당일 대응 및 대기 인원 최종 결정`

## 9. 추가로 결정해야 할 사항

- 21시 이후 당일 대응 여부를 결정하는 최종 결정권자는 누구인가?
- 결정권자가 부재할 경우 대체 의사결정자는 누구인가?
- 팀장별 이슈 확인 및 회신 시점은 어떻게 할 것인가?
- 22시 이후 추가 이슈가 발생했을 때 대응 기준은 무엇인가?
- Block / Development / Polishing 분류를 언제부터 공식 적용할 것인가?
- 중간점검 빌드와 실제 개발 마감 빌드의 운영 기준을 어떻게 분리할 것인가?

## 10. 포트폴리오 기록 방향

현재는 개선 효과를 확정하지 않고 **문제 정의 및 프로세스 개선 진행 사례**로 기록한다.

향후 측정할 지표:
- 중간점검 평균 종료 시간
- 22시 이후 잔류 인원 수
- 빌드별 이슈 수
- Block 이슈 수
- 다음 날 이월 이슈 수
- 계획 대비 실제 반영률
- 팀장 확인 회신률
- 추가 빌드 발생 횟수

최종 포트폴리오 구조:

`Problem → Analysis → Action → Iteration → Result`
