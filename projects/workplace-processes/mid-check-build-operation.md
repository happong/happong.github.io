# Dev Build 중간점검 운영 프로세스 개선

> 상태: 진행 중
> 시작일: 2026-09-10
> 목적: Dev Build 중간점검에서 발생하는 일정·품질·대기 인원·의사결정 문제를 실제 협의 과정까지 포함해 기록하고, 이후 운영 결과를 바탕으로 지속 개선한다.

---

## 1. 배경

프로젝트는 개발 초창기 단계이므로 Dev Build에 개발 중인 기능과 리소스가 계속 반영된다. 따라서 중간점검 빌드에서 버그가 발생하는 것 자체는 자연스러운 상황이다.

문제는 버그의 존재 자체보다 **언제까지 무엇을 확인할 것인지, 발견된 문제를 누가 판단할 것인지, 누가 대응해야 하는지, 언제 업무를 종료할 것인지**가 명확하지 않은 상태에서 운영이 이루어진다는 점이었다.

기존에는 원래 개발 마감 일정이 있었지만 일정 및 품질 지연에 대응하기 위해 주간 중간점검을 운영하게 되었고, 점검일에는 개발자들이 계속 작업을 이어가면서 빌드에 추가 내용이 들어가는 상황이 반복되었다.

---

## 2. 최초 관찰한 문제

### 2-1. 중간점검 범위가 명확하지 않음

주간 중간점검은 존재했지만, 해당 빌드에서 **무엇을 반드시 확인해야 하는지 / 무엇까지 수정해야 하는지 / 무엇은 다음 단계로 넘겨도 되는지**가 명확하지 않았다.

예를 들어 수요일에 사실상 빌드가 닫히는 시점이 있다고 생각했지만, 그 이후에도 새로운 작업이 계속 들어가면서 기존에 확인했던 내용에 사이드 이펙트가 발생하고 이를 다시 수정하는 일이 생겼다.

즉, '마감'이라는 표현은 있었지만 실제로는 범위가 닫히지 않은 상태였다.

### 2-2. 정해진 시간까지 전원이 대기하는 구조

중간점검 빌드와 직접적인 관련이 없는 인원도 특정 시간까지 대기하는 상황이 발생했다.

실제로 대응이 필요한 사람이 누구인지보다 **'오늘은 몇 시까지 있어야 하는가'**가 먼저 작동하는 형태였다.

처음에는 이를 '의미 없는 야근'으로 볼 수도 있었지만, 문제를 더 객관적으로 분석하면 핵심은 근무시간 자체가 아니라 **대기 기준과 대응 범위가 정의되어 있지 않은 것**이었다.

### 2-3. 마감 이후 업무가 자연스럽게 다음 날로 넘어감

수요일에 마감 시점이 존재하는 것처럼 운영되었음에도 미완료 항목이 목요일 오전까지 넘어가는 경우가 있었다.

그 과정에서 '오늘 반드시 해결해야 하는 문제'와 '다음 단계에서 해결해도 되는 문제'의 구분이 명확하지 않았다.

### 2-4. 의사결정 주체가 명확하지 않음

중간점검에서 발견된 이슈를 두고 다음과 같은 질문에 대한 명확한 기준이 없었다.

- 이 이슈는 오늘 반드시 수정해야 하는가?
- 담당자가 계속 대기해야 하는가?
- 개발 중인 기능이 조금 부족해도 이번 점검을 통과시켜도 되는가?
- 22시 이후에도 작업을 계속해야 하는가?
- 업무를 종료한다고 최종 판단할 사람은 누구인가?

PM이 전체 상황을 조율하는 과정에서 사실상 QA와 종료 판단까지 맡게 될 가능성이 있었다.

---

## 3. 문제를 '야근'이 아니라 '운영 구조'로 재정의

처음 문제의식은 '중간점검 때문에 의미 없는 야근이 발생한다'는 것이었지만, 이를 그대로 개선안의 핵심으로 가져가지는 않았다.

객관적으로 보면 야근을 줄이는 것 자체가 목적이 되어서는 안 된다. 프로젝트 초기에는 실제로 긴급 대응이 필요한 상황이 존재할 수 있기 때문이다.

따라서 문제를 다음과 같이 재정의했다.

> **중간점검 빌드의 검증 범위, 이슈 대응 기준, 업무 종료 기준, 의사결정 주체가 명확하지 않아 필요한 인원과 불필요한 인원이 동일하게 대기하고, 빌드가 반복적으로 수정되는 구조가 발생한다.**

이렇게 정의하면 목표는 '일찍 퇴근시키기'가 아니라 **필요한 사람만 필요한 시점까지 대응하도록 운영 구조를 만드는 것**이 된다.

---

## 4. 최초 개선안: Check Scope Freeze

### 4-1. 기본 개념

개발 자체를 중단하는 'Development Freeze'가 아니라, **중간점검에서 확인할 범위를 Freeze**하는 방식으로 접근했다.

핵심 흐름은 다음과 같다.

`계획 → 마감 → 안정화 → 검증`

각 단계의 의미:

1. **계획**: 이번 중간점검에서 반드시 확인할 리소스/기능을 사전에 정한다.
2. **마감**: 점검 대상 범위에 대한 반영 시점을 명확히 한다.
3. **안정화**: 새로 추가된 내용과 수정사항을 반영하고 빌드를 안정화한다.
4. **검증**: 정해진 범위만 실제로 확인한다.

### 4-2. 점검 범위 판단 기준

이번 주에 계획한 내용에 대해 다음 세 가지를 확인하도록 했다.

1. 이번 주까지 하기로 한 내용이 실제로 반영되었는가?
2. 반영된 내용이 최소한 정상적으로 동작하는가?
3. 문제가 있다면 다음 단계까지 해결 가능한 수준인가?

### 4-3. 계획 상태

화요일까지 중간점검에서 확인할 필수 대상을 정하고 담당자가 상태를 표시하는 방식을 생각했다.

- 이번 주 완료 예정
- 이미 완료
- 개발 중
- 다음 주로 넘어갈 가능성 있음

수요일 오전에는 추가 확인을 하고, 수요일 오후에 새롭게 추가된 내용은 필수 중간점검 대상에서 제외하는 방향을 제안했다.

새로운 작업을 무조건 막는 것이 아니라, **새로 들어온 작업 때문에 기존 점검 범위가 계속 변하지 않도록 하는 것**이 목적이었다.

## 5. 이슈 분류를 단순화

프로젝트가 아직 초기 단계이므로 일반적인 Major / Minor 등의 결함 등급을 적용하기보다 실제 대응 판단에 필요한 세 가지로 단순화하는 방향을 제안했다.

### Block

당일 대응이 필요한 문제.

예:
- 실행 자체가 안 됨
- 빌드 실패
- 핵심 기능 진입 불가
- 다른 담당자의 작업을 막음
- 필수 중간점검 검증을 진행할 수 없음
- 정상적인 빌드 확인 자체를 방해함

### Development

당일 즉시 수정할 필요는 없지만 개발이 더 필요한 문제.

예:
- 구현 미완료
- 연동 미완료
- 로직/데이터 추가 개발 필요
- 개발 진행 중인 기능의 잔여 작업

### Polishing

중간점검에서 확인은 하지만 마감 여부와 직접 연결되지 않는 개선사항.

예:
- UI 디테일
- 연출 수정
- 표현/문구 수정
- 리소스 품질 개선
- 수치 튜닝

핵심은 '이슈가 있느냐'가 아니라 **'오늘 반드시 대응해야 하느냐'**를 구분하는 것이다.

## 6. 최초 대기 인원 운영안

최초에는 다음과 같이 대기 인원을 구분하는 방안을 생각했다.

### 필수 대기
- 새 기능을 반영한 담당자
- Block 이슈 담당자
- 해당 기능과 직접 연결된 핵심 시스템 담당자
- 빌드/머지 담당자

### 선택 대기
- 당일 수정 가능성이 높은 담당자
- 연계 작업으로 인해 대기 가능성이 있는 담당자

### 대기 해제
- 당일 변경사항이 없는 인원
- 해당 영역에서 이슈가 없는 인원
- 긴급 대응과 직접 관련이 없는 인원

이를 통해 '전원 대기'에서 '필요 인원만 대기'로 전환하는 것을 목표로 했다.

---

## 7. 최초 빌드 운영안

처음 생각한 운영은 빌드가 생성되는 시점과 사람이 확인하는 시점을 구분하는 것이었다.

### Timer Build

- 03:00 빌드
- 15:00 빌드

03:00 / 15:00은 사람이 그 시간에 모여 확인한다는 의미가 아니라 **자동/예약 빌드가 생성되는 기준 시점**으로 정의했다.

### 오후 운영

- 18:00: 당일 대응 범위 정리
- 20:00: Block 수정사항 확인
- 22:00: 예외적으로 미해결 Block이 있는 경우에만 추가 대응
- 다음 날 오전: 전날 미해결 사항 재확인

이 단계에서 중요한 생각은 **18시를 '빌드가 나온 시간'과 '모든 업무가 종료되는 시간'을 동일하게 보지 않는 것**이었다.

## 8. 팀장과 최초 협의

팀장에게 `계획 → 마감 → 안정화 → 검증` 구조와 Check Scope Freeze 개념을 공유했다.

팀장 의견은 다음과 같았다.

> 계획 → 마감 → 안정화 → 검증 단계도 필요할 것 같지만 아직 초창기이고 매주 밀어넣기 바빠서 순차적으로 적용될 수 있게 관리되어야 할 것 같다.

이에 따라 Check Scope Freeze 전체를 한 번에 강제 적용하기보다 **우선 빌드 일정부터 명확하게 잡는 방향**으로 진행했다.

### 팀장과 합의한 빌드 일정

수요일:
- 03:00
- 11:00
- 15:00
- 18:00
- 추가 요청 시 추가 빌드

목요일:
- 03:00
- 11:00

이 시점에서는 빌드 일정 자체는 명확해졌지만, **각 빌드가 업무 마감과 어떤 관계인지**까지는 충분히 정의되지 않았다.

## 9. 09/09 중간점검 공지

실제 운영을 위해 다음과 같이 공지했다.

> `[공지] M1_3 2차 중간 점검 일정 공지`
>
> `09/10(목) 15시에 중간 점검이 진행될 예정이므로, 09/09(수)까지 계획된 리소스가 정상으로 출력되는지 빌드에서 확인 부탁드리겠습니다.`

수요일 빌드 일정은 다음과 같이 안내했다.

- 03:00 1차
- 15:00 2차
- 18:00 3차 → 수요일 마감 빌드

그리고 다음 조건에서는 추가 빌드를 진행한다고 안내했다.

> 5차 빌드 후 크리티컬 이슈(진행 불가 건) 발생 및 추가 빌드 요청이 있는 경우 추가 빌드 진행

목요일:
- 03:00 4차
- 11:00 5차

이 공지에서 **18시를 '수요일 마감 빌드'라고 표현한 것이 이후 인식 차이의 원인이 되었다.**

## 10. 실제 협의 과정에서 발생한 인식 차이

팀장으로부터 다음 요청을 받았다.

> "하은님 8시 추가 빌드도 안내 부탁드릴게요~ 오늘 어차피 10시 마감이니께 저렇게 물어보시면 중간에 한번 더 말아주셔요"

PM은 기존 공지를 기준으로 18시 빌드 이후에는 추가 요청이 없는 경우 마무리되는 것으로 이해하고 있었기 때문에 다음과 같이 확인했다.

> "추가로 없으면 마무리 하는걸로 이해를 했었는데 10시까지 계속 진행하면 될까요?!"

팀장 답변:

> "10시까지는 빌드 대응 필요한것들은 봐야죠 'ㅁ'"

이에 PM은 다음과 같이 응답했다.

> "넵 그럼 사전 공지를 10시까지로 하는게 맞을 것 같아서 제가 이해를 잘못했네요! 다음 공지할때는 반영해서 공지하겠습니다~!"

그러자 팀장이 다시 질문했다.

> "음? 사전 공지 10시가 뭔가요? 'ㅁ'"

PM은 기존 공지를 보여주며 다음과 같이 설명했다.

> "이렇게 공지가 된 상태라 사람들이 오해할 수 있어서요"

팀장 답변:

> "아 네네 저거 보고 왔는데 아 근데 10시까지 빌드 이슈 대응은 다들 알고 계신거 아니었나요> 요건 PD님이 공지 하신거라"

PM:

> "네네 근데 혼란이 올수도 있을 것 같아서 내용을 통일하는게 좋지 않을까 싶습니다"

팀장 최종 답변:

> "아하 네네 수요일 마무리 빌드가 6시 군요 18시를 마무리라고 생각하지는 않았는데 마감일 10시 대기 유지여서 빌드 일정만 8시 추가 하시면 될듯합니다."

## 11. 협의에서 확인된 핵심 문제

이 대화를 통해 PM이 잘못 이해한 부분과 조직의 운영상 모호한 부분을 분리할 필요가 있었다.

### PM 측의 개선점

- '18시 마감 빌드'를 '18시 이후 대응 종료'와 연결해서 해석했다.
- 빌드 생성 시간과 업무 대응 종료 시간을 사전에 명확하게 분리하지 않았다.
- Check Scope Freeze에서 정의한 운영 원칙과 기존 조직의 22시 대기 관행을 하나의 운영안으로 완전히 통합하지 못했다.

### 조직 측의 개선점

- '22시까지 빌드 이슈 대응'이 공식 운영 기준인지 기존 관행인지 명확하지 않았다.
- 18시 빌드가 단순 빌드 생성 시점인지 수요일 마감인지 공통된 의미가 없었다.
- 22시까지 대기해야 하는 인원과 그렇지 않은 인원의 기준이 명확하지 않았다.
- 22시 이후 추가 대응 여부를 누가 최종 결정하는지 명확하지 않았다.

따라서 이 문제는 한쪽의 단순한 실수가 아니라 **동일한 용어를 서로 다른 운영 의미로 해석한 R&R/프로세스 정의 문제**로 보는 것이 타당하다.

## 12. 추가로 확인된 과거 운영 사례

이전에도 22시 빌드 이후 업무 종료에 대한 명확한 의사결정이 이루어지지 않은 사례가 있었다.

PM이 다음과 같이 안내했다.

> "10시 빌드 완료되면 간단히 플레이 체크 후 나머지 이슈는 명일 오전빌드로 진행하려고 합니다. 의견 부탁드리겠습니다~!"

그러나 팀장들의 명확한 회신이 없었고, 결과적으로 구성원들은 23시 30분까지 대기했다.

이후 PM이 다음과 같이 다시 공지하면서 실제 업무를 종료하는 방향으로 정리했다.

> "현재 22시 빌드에서 잔여이슈입니다. 해당 이슈는 금일 수정해주시면 명일 새벽 빌드로 오전에 확인하고 금일은 마무리 하도록 하겠습니다"

이 사례에서 확인되는 문제는 PM이 실제로 **최종 의사결정권을 가진 것은 아니지만, 결정권자의 명확한 응답이 없으면 결국 PM이 종료 판단을 떠안게 되는 구조**라는 점이다.

따라서 향후에는 PM이 단독으로 종료를 결정하기보다, **PM은 현황을 정리하고 결정권자에게 판단을 요청하며, 결정된 내용을 운영하는 역할**로 분리할 필요가 있다.

## 13. 다음 개선안: PM의 직접 QA 제거

추가 논의에서 가장 중요한 개선 방향은 **PM팀이 빌드 상태를 직접 확인하고 이슈를 판정하는 역할을 제거하는 것**이다.

기존 구조에서는 PM이 빌드를 직접 확인하면서 다음과 같은 업무가 섞일 수 있었다.

`빌드 일정 관리 + QA + 이슈 발견 + 이슈 우선순위 판단 + 대응 인원 판단 + 종료 판단`

이를 다음과 같이 분리한다.

### PM팀

`빌드 일정 관리 → 각 팀 확인 요청 → 이슈/대응 현황 취합 → 전체 현황 공유 → 결정사항 전달 및 대기 인원 운영`

PM은 각 팀의 전문 영역을 직접 QA하지 않는다.

### 각 팀장

`담당 영역 확인 → 이슈 확인 → 수정 필요 여부 판단 → 담당자 지정 → 수정 완료 확인`

각 팀이 자기 영역의 품질에 1차 책임을 가진다.

### 팀장/AD

`당일 대응 여부 판단 → 대기 인원 최종 결정 → 추가 대응/종료 결정`

이 구조의 핵심은 PM이 책임을 회피하는 것이 아니라 **판단의 전문성과 의사결정 권한을 실제 담당 조직으로 되돌리는 것**이다.

## 14. 현재 논의 중인 운영 프로세스

### 빌드 일정

- 03:00
- 15:00
- 18:00
- 20:00
- 21:00
- 22:00 이후 대기 해제 여부 결정

### 15시 빌드

PM이 각 팀장에게 담당 영역 확인을 요청한다.

각 팀장은:
- 담당 영역을 직접 확인
- 수정이 필요한 이슈를 정리
- 담당자 지정
- 당일 대응 여부 판단

PM은 결과를 취합한다.

### 18시 빌드

기존 이슈의 수정 상태와 새롭게 확인된 이슈를 각 팀에서 확인한다.

PM은 다시 각 팀의 결과를 취합하고 전체 상태를 공유한다.

### 20시 빌드

당일 대응 대상으로 분류된 이슈의 수정 진행 상황을 확인한다.

이 단계에서는 모든 이슈를 해결하려는 것이 아니라 **현재 대응 중인 이슈가 실제로 진행되고 있는지 확인**하는 데 초점을 둔다.

### 21시 빌드

각 팀장은 담당 영역의 이슈를 기준으로 다음을 정리한다.

- 오늘 반드시 대응해야 하는 이슈
- 다음 빌드/다음 날로 넘겨도 되는 이슈
- 현재 수정 완료된 이슈
- 담당자가 계속 대기해야 하는지 여부

PM은 이를 취합한다.

### 22시

22시는 '무조건 전원이 퇴근하는 시간' 또는 '무조건 전원이 일하는 시간'이 아니라 **전원 대기 상태에서 필요한 인원만 잔류할지 결정하는 의사결정 시점**으로 정의하는 방향이다.

팀장/AD가 최종적으로:
- 추가 대응이 필요한 이슈
- 계속 대기해야 하는 담당자
- 추가 대응이 필요하지 않은 인원
- 업무 종료 여부

를 판단한다.

PM은 결정된 내용을 전달하고, 대기 해제 대상자에게 종료를 안내한다.

## 15. 이슈 관리 리스트

향후에는 PM이 직접 이슈를 판단하기보다 각 팀이 전달한 정보를 아래 형태로 취합한다.

| 이슈 | 담당팀 | 담당자 | 상태 | 당일 대응 | 분류 | 비고 |
|---|---|---|---|---|---|---|
| A 기능 진입 불가 | 시스템 | 담당자 | 미수정 | O | Block | 중간점검 진행 불가 |
| B UI 오류 | UI | 담당자 | 수정중 | X | Development | 다음 빌드 확인 |
| C 연출 수정 | 아트 | 담당자 | 미수정 | X | Polishing | 차주 반영 |
| D 데이터 오류 | 기획 | 담당자 | 수정완료 | - | Block | 21시 재확인 |

가장 중요한 필드는 **당일 대응 여부**이다.

이슈가 존재한다는 사실만으로 전원이 계속 대기하는 것이 아니라, 해당 이슈가 오늘 해결되어야 하는지 판단하도록 한다.

## 16. 의사결정권자 부재 문제

현재 구조에서 반드시 추가로 정의해야 하는 부분이다.

결정권자가 부재한 경우에도 PM이 임의로 최종 판단하게 되면 기존 문제가 반복된다.

따라서 다음을 명시할 필요가 있다.

1. 기본 결정권자: 팀장/AD
2. 결정권자 부재 시 대체 결정권자: 별도 지정 필요
3. 대체 결정권자도 없을 경우 기본 운영 원칙: 별도 합의 필요

이 항목이 정의되지 않으면 PM의 역할 분리를 해도 결국 PM이 최종 결정을 떠안게 된다.

## 17. 현재 R&R 정의

| 역할 | 책임 |
|---|---|
| PM | 빌드 일정 관리, 각 팀 확인 요청, 결과 취합, 현황 공유, 결정사항 전달, 대기 인원 운영 |
| 각 팀장 | 담당 영역 확인, 이슈 확인, 수정 필요 여부 판단, 담당자 지정, 수정 완료 확인 |
| 팀장/AD | 당일 대응 여부, 잔류 인원, 추가 대응 및 종료 여부 최종 결정 |

핵심 구조:

`PM = 운영/조율`

`각 팀 = 품질 확인/이슈 판단`

`팀장·AD = 의사결정`

## 18. 이번 개선에서 중요한 관점

이번 사례에서 목표를 단순히 '야근 감소'로 잡으면 설득력이 약해진다.

더 정확한 목표는 다음과 같다.

> **필요한 이슈에는 필요한 인원이 대응하고, 대응할 필요가 없는 인원은 명확한 기준에 따라 대기에서 해제할 수 있도록 운영 구조를 만드는 것.**

따라서 성과 역시 단순히 퇴근 시간이 빨라졌는지만 보는 것이 아니라 다음과 같이 측정할 필요가 있다.

- 22시 이후 잔류 인원 수
- 22시 이후 실제 대응 이슈 수
- 추가 빌드 발생 횟수
- 빌드별 이슈 수
- Block 이슈 수
- 다음 날 이월 이슈 수
- 계획 대비 실제 반영률
- 각 팀 확인 회신률
- PM 직접 QA 건수
- PM이 단독으로 종료 판단한 건수

## 19. 포트폴리오화 방향

이 사례는 단순한 '빌드 일정 관리' 사례보다 **프로세스의 책임과 의사결정 구조를 재설계한 사례**로 발전시키는 것이 적합하다.

### Problem

빌드 일정은 존재했지만 검증 범위, 이슈 대응 기준, 종료 기준, 의사결정 주체가 불명확했다.

### Analysis

반복되는 빌드 수정과 전원 대기 현상을 단순 인력 문제로 보지 않고, Scope / R&R / Decision Right 문제로 분해했다.

### Action

- Check Scope Freeze 제안
- Block / Development / Polishing 기준 제안
- 빌드 일정 고정
- PM 직접 QA 제거 방향 제안
- 각 팀장 1차 검증 책임 부여
- 팀장/AD의 당일 대응 및 대기 인원 결정 권한 명확화

### Iteration

최초 운영안에서 18시 빌드와 22시 업무 대응 마감의 의미가 충돌하는 문제를 발견했고, 이를 계기로 빌드 생성 시간과 업무 대응 종료 시간을 분리하는 방향으로 수정했다.

### Result

현재는 운영 적용 단계이므로 정량적 성과를 확정하지 않는다. 이후 실제 운영 데이터를 축적해 결과를 업데이트한다.
