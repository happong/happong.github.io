## 1. 이번 Iteration이 발생한 배경

기존 중간점검 운영 개선에서는 `계획 → 마감 → 안정화 → 검증` 흐름을 만들고, 빌드 일정과 R&R을 먼저 명확하게 하는 방향으로 순차 적용하기로 했다.

그러나 Dev 브랜치 자체는 현재 개발 중인 작업이 계속 반영되는 구조이기 때문에, 중간점검을 위한 검증이 끝난 이후에도 새로운 변경사항이 들어갈 수 있다.

그 결과 **이미 수정하거나 정상 확인했던 이슈가 이후 빌드에서 다시 발생하는 사례**가 확인되었다.

이번 Iteration의 핵심 질문은 다음과 같다.

> Dev 브랜치에서 개발을 계속 진행하면서도, 중간점검을 위해 이미 검증한 상태를 어떻게 안정적으로 유지할 것인가?

## 2. 문제 1 — N 등장 컷신 이후 미출현

### 2-1. 실무자 대화 원문

> 방금 테스트 했는데, N 등장 컷신을 스킵하면 N이 안나옵니다
>
> 등장연출 스킵안했을때 잘나왔던걸로 기억되는데 스킵했을때 문제가되는거면 연출쪽에서 대응할수있는게 없을꺼같습니다 같이 확인해봐야할꺼같아요
>
> 음 어제 그랬는데..오늘 잘 나오다가 또 저러네요 ㄷㄷ

### 2-2. 6W1H

**언제**
- 어제 동일 현상이 발생한 것으로 공유됨.
- 오늘 정상 동작한 시점이 있었으나 다시 동일 현상이 발생함.
- 정확한 빌드/변경 시점은 추가 확인 필요.

**어디서**
- Dev Build로 추정.
- N 등장 컷신 및 컷신 스킵 조건.
- 정확한 빌드 번호는 미확인.

**무엇을**
- 등장 컷신을 스킵했을 때 N이 등장하지 않는 현상.
- 스킵하지 않았을 때는 정상 동작했던 것으로 기억됨.

**누가**
- 테스트 및 최초 발견 실무자.
- 관련 연출/기능 담당자들이 함께 확인해야 하는 상황.
- 최종 원인 담당자는 아직 미확정.

**어떻게**
- 컷신 스킵 여부에 따라 결과가 달라지는 것으로 관찰됨.
- 동일 현상이 어제 발생 → 오늘 정상 → 다시 발생하는 비일관성이 있음.

**왜**
- 현재 미확인.
- 컷신 스킵 로직 자체의 문제인지, 다른 변경사항과의 상호작용인지, 데이터/상태 문제인지 확인 필요.
- Dev의 후속 변경이 원인이라는 것도 현재는 가설일 뿐임.

## 3. 문제 2 — Souldrive 미차감

### 3-1. 실무자 대화 원문

> Souldrive 안빠짐 문제 제기
>
> souldrive 저번에 수정했는데 다시 확인해보겠습니다.

### 3-2. 6W1H

**언제**
- 이전에 수정했던 이슈가 현재 다시 확인됨.
- 최초 수정 및 정상 확인 시점은 추가 확인 필요.

**어디서**
- Dev Build로 추정.
- Souldrive 관련 기능.

**무엇을**
- Souldrive가 정상적으로 차감되지 않는 현상.
- 과거 수정 이력이 있는 이슈.

**누가**
- 이슈 발견자 및 Souldrive 담당자가 확인.

**어떻게**
- 이전 수정 이후 동일 현상이 재확인됨.
- 정확한 재현 조건과 변경 이력은 추가 확인 필요.

**왜**
- 원인 미확인.
- 이전 수정이 완전하지 않았거나, 후속 변경으로 기존 수정 조건이 깨졌거나, 다른 시스템 변경과의 상호작용일 가능성이 있음.

## 4. 현재 확인된 공통 현상

두 사례에서 현재 사실로 볼 수 있는 것은 다음과 같다.

1. Dev Build에서는 개발 중인 작업이 계속 반영된다.
2. 이미 발생했던 이슈가 다시 확인되는 사례가 있다.
3. N 이슈는 동일 현상이 정상/비정상으로 변해 재현 상태가 불안정하다.
4. Souldrive는 이전 수정 이력이 있는 이슈가 재확인되었다.
5. 현재 정보만으로 Dev의 특정 변경이 직접 원인이라고 단정할 수 없다.

따라서 현재 문제 정의는 다음과 같이 설정한다.

> **Dev 브랜치에서 변경이 지속되는 환경에서, 이미 수정·검증한 상태가 후속 변경 이후에도 유지되는지 추적하고 보장하기 어려워 재발 이슈의 원인과 책임 범위를 다시 확인해야 하는 상황이 발생하고 있다.**

## 5. 기존 의견과의 관계

이전에 브랜치 분리 의견을 검토했을 때 다음과 같은 우려가 있었다.

- 현재 프로젝트는 개발 초기 단계임.
- 개발 중인 작업이 많음.
- 브랜치를 분리하면 관리 공수가 증가함.
- 현재 단계에서 별도 브랜치 운영은 과할 수 있음.

이 판단은 초기 개발 단계의 특성을 고려하면 합리적인 반론이다.

따라서 이번 Iteration에서는 기존 판단을 틀렸다고 전제하지 않는다.

다만 실제 운영 과정에서 **브랜치 분리를 하지 않았을 때 발생하는 비용도 존재하는지**를 새롭게 비교할 필요가 생겼다.

---

## 6. 문제를 브랜치가 아닌 '검증 상태 유지' 관점으로 재정의

현재 단계에서 바로 `브랜치를 만들어야 한다`고 결론내리지 않는다.

먼저 해결해야 하는 요구사항은 다음과 같다.

> **중간점검에서 정상으로 검증한 상태가 이후 개발 변경 때문에 무의미해지지 않도록 검증 범위를 보호할 수 있어야 한다.**

가능한 방법은 여러 가지다.

### A. 현행 Dev 유지
- Dev에서 계속 개발.
- 이슈 발생 시 재수정.
- 추가 빌드와 재검증으로 대응.

### B. 부분적인 변경 통제
- 특정 시점 이후 중간점검 대상 기능의 변경을 제한.
- 필요한 변경만 명시적으로 허용.
- 별도 브랜치 없이 운영 규칙으로 통제.

### C. 중간점검 안정화 브랜치
- Dev는 계속 개발.
- 특정 시점에 중간점검 대상 상태를 분기.
- 분기된 브랜치에서 안정화/수정/검증.
- 점검 이후 결과를 Dev에 반영.

### D. Feature 단위 브랜치 + 선택적 반영
- 모든 개발을 Dev에 직접 반영하지 않고 작업 단위로 분리.
- 중간점검 대상만 Dev 또는 안정화 영역에 선택적으로 반영.

현재는 C가 반드시 정답이라고 판단하지 않는다.

---

## 7. 대안 비교를 위한 확인 항목

브랜치 분리를 설득하기 전에 다음 데이터를 수집한다.

### 현재 방식의 비용
- 기존 수정 이슈의 재발 횟수
- 재발 이슈의 재수정 시간
- 추가 빌드 횟수
- 동일 이슈 재검증 횟수
- 원인 추적에 사용한 시간
- 관련 인원 수
- 중간점검 이후 발생한 변경사항 수

### 브랜치 방식의 예상 비용
- 브랜치 생성/관리 시간
- Merge/Cherry-pick 등 추가 작업
- 브랜치 간 충돌 가능성
- 담당자 교육/운영 규칙 추가
- CI/CD 또는 빌드 설정 변경 필요 여부

핵심 비교 기준은

> **브랜치 관리 공수 vs 현재 방식의 재작업·재검증 공수**

로 한다.

## 8. 추가로 확인해야 하는 Fact

현재는 아래 정보가 부족하다.

- N 이슈가 정상 → 재발한 사이의 정확한 빌드 번호
- 정상 확인 이후 Dev에 반영된 commit/change
- Souldrive 수정 commit과 재발 빌드 사이의 변경사항
- 두 이슈와 관련된 시스템의 공통 변경 여부
- 동일 유형의 재발 사례가 이전에도 몇 건 있었는지
- 재발이 Dev 변경과 실제 시간적/기술적으로 연결되는지

따라서 **현재 단계에서 'Dev 브랜치가 원인'이라는 표현은 사용하지 않는다.**

---

## 9. 다음 행동

1. 이번 두 사례를 이슈 기록에 남긴다.
2. 정상 확인 빌드와 재발 빌드를 확인한다.
3. 두 시점 사이의 Dev 변경 이력을 확인한다.
4. 같은 유형의 재발 사례를 추가 수집한다.
5. 현재 방식에서 발생하는 재작업 비용을 기록한다.
6. 팀장에게 문제 현상을 먼저 공유한다.
7. 브랜치 분리 자체가 아니라 **검증 상태 유지 방안**으로 논의한다.
8. 가능하면 다음 중간점검에서 제한적인 Pilot을 제안한다.
9. Pilot 결과를 기존 방식과 비교한다.

## 10. 팀장 협의 시 사용할 핵심 논리

> 이전에 브랜치 분리에 대해서는 현재 개발 단계에서 관리 공수가 커질 수 있다는 의견이 있었고, 그 부분은 저도 이해하고 있습니다.
>
> 다만 최근 중간점검을 운영하면서 이미 수정했던 이슈가 다시 확인되거나, 같은 현상이 정상/비정상으로 바뀌는 사례가 발생하고 있습니다.
>
> 그래서 지금은 브랜치를 반드시 만들어야 한다는 것보다, 중간점검에서 검증이 끝난 상태를 이후 개발 변경으로부터 어떻게 유지할 수 있을지를 다시 검토해보면 좋을 것 같습니다.
>
> 전체 개발 브랜치를 분리하는 방식이 부담스럽다면, 우선 중간점검 기간에 한해서 안정화 영역을 별도로 운영하는 방식도 있을 것 같습니다.
>
> 다음 중간점검에서 한 번 Pilot으로 적용해보고, 브랜치 관리에 들어가는 공수와 재발 이슈/추가 빌드/재검증이 실제로 얼마나 발생하는지 비교한 뒤 유지 여부를 판단하는 방법도 가능할 것 같습니다.

## 11. 현재 판단

**상태: 분석 중**

> 브랜치 분리가 필요하다는 가설은 재검토할 가치가 있다. 그러나 현재 확인된 두 사례만으로 브랜치가 직접적인 해결책이라고 단정하지 않는다.
>
> 먼저 변경 이력을 통해 재발과 Dev 변경의 관계를 확인하고, 현행 방식의 재작업 비용을 측정한 뒤 제한적 Pilot 여부를 결정한다.

이후 실제 협의 결과와 운영 결과를 이 문서에 계속 추가한다.
