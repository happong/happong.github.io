## 1. 면담 전 제안의 핵심

면담 전 문제 프레임은 다음과 같았다.

- 검증 범위가 계속 변함
- 개발 중인 상태와 검증 대상이 혼재함
- 이슈 발생 시 당일 대응 여부/다음 단계 이관 기준이 불명확함
- PM이 현황 정리와 의사결정을 함께 떠안는 상황이 발생함
- Dev Branch에서 개발 변경이 계속 반영되어 검증 상태가 유지되지 않을 가능성이 있음
- 제안: `계획 → 마감 → 안정화 → 검증`, R&R 분리, 검증 상태 보호를 위한 Branch Pilot

면담 전에는 중간점검의 검증 상태를 어느 정도 고정하여 안정화/검증하는 방향을 상정했다.

---

## 2. 면담에서 확인된 가장 중요한 사실 — 중간점검의 목적 재정의

리드의 설명에 따르면 현재 중간점검의 목적은 **마일스톤 마감처럼 특정 상태를 고정하여 완성도를 검증하는 것**이 아니다.

중간점검의 목적은 다음과 같다.

- 개발 진행 중인 상태를 중간에 확인한다.
- 현재 빌드가 어느 정도까지 왔는지 확인한다.
- 빠진 요소를 발견한다.
- 발견한 문제 중 필요한 것은 챙겨서 개발을 더 빠르게 진행한다.
- 개발 진행 중이므로 어제 정상인 상태가 오늘 다시 깨지는 현상 자체는 발생할 수 있다.
- 현재는 긴급 Block 이슈 위주로 대응하고, 그 외 이슈는 이후 단계로 미룬다.

따라서 기존 문서에서 중간점검을 `계획 → 마감 → 안정화 → 검증`의 마지막 단계에서 **검증 상태를 고정하는 운영**처럼 표현한 것은 현재 프로젝트의 실제 목적과 일부 맞지 않는다.

### 중요 수정

기존 가설:
> 중간점검은 특정 시점의 안정화된 상태를 기준으로 검증해야 한다.

면담 후 이해:
> 중간점검은 개발 진행도를 확인하고 빠진 요소를 발견하기 위한 **Progress Check**에 가깝다. 완성 상태를 고정하는 마일스톤 검증과는 목적이 다르다.

이 차이를 향후 문서와 면담 설명에 반영해야 한다.

## 3. Branch 제안에 대한 실제 피드백

### 리드의 판단

현재 중간점검을 위해 별도 Branch를 따서 관리하는 것은 **현 단계에서는 불필요한 관리 공수**로 판단한다.

이유:

- 프로젝트가 아직 초기 단계임.
- 개발이 계속 진행되고 있음.
- 중간점검에서 어제 정상인 것이 오늘 깨지는 것은 현재 단계에서 감수하고 있음.
- 긴급 Block 이슈만 우선 대응하고, 그 외 이슈는 다음 단계로 넘기는 방식으로 이미 운영하고 있음.
- Branch를 별도로 관리하는 공수가 현재 중간점검의 목적 대비 과함.

따라서 **중간점검용 안정화 Branch Pilot은 현재 합의되지 않았다.**

### Branch가 필요한 시점에 대한 리드의 설명

Branch 관리는 향후 실제 마감 단계에서 필요하다.

언급된 기준:

- 10월 7일 리소스 마감
- 10월 21일 개발 마감

이 시점에는 마감 대상 리소스/개발 범위를 관리하기 위한 Branch 전략이 필요할 수 있다.

특히 마감에 영향을 줄 수 있는 M2 작업이 진행 중이라면 해당 변경을 무조건 Dev에 올리는 것이 아니라, 마감에 영향을 주는지 판단한 후 반영 여부를 관리해야 한다.

향후에는:

- 안정화 Branch를 언제 생성할지
- Dev에서 작업할지 Branch에서 작업할지
- Merge 비용을 어느 정도로 줄일 수 있는지
- 프로그램팀에서 실제 Merge/Branch 관리 공수가 얼마나 드는지

를 함께 판단할 필요가 있다.

### 면담 중 사용자의 보완 설명

사용자는 Branch를 계속 유지하려는 목적이 아니라, **당일 특정 시점의 검증 상태를 일회성으로 보존하고 다음날 문제가 커졌을 경우 이전 빌드로 돌아가 비교할 수 있는 방식**을 생각했다고 설명했다.

리드는 이 방식 자체의 개념은 이해했지만, 현재 중간점검 목적에서는 별도 Branch 관리가 필요하지 않다는 입장이다.

## 4. 의사결정권/R&R에 대한 실제 피드백

이 부분은 면담 전 가설과 실제 조직 운영 방식 사이에 중요한 차이가 확인되었다.

### 면담 전 가설

> 당일 대응 여부를 누가 결정하는지 명확하지 않아 팀장/AD의 결정이 발생하지 않고 PM이 상황을 마무리하는 구조가 문제다.

### 면담 후 확인된 실제 운영 의도

리드 설명상 의사결정은 하나의 주체가 모두 가져가는 것이 아니라 **이슈 성격에 따라 1차 판단과 리드 판단이 나뉜다.**

예:

- 게임 진행 자체를 막는 Block 이슈 → 빠르게 수정 요청
- 1차적으로 리드 단에서 이슈 대응 필요 여부 판단
- 작은 퀄리티 이슈이거나 특정 리드가 반드시 보여달라고 요청한 항목 → 해당 리드/담당자가 완성도와 대응 여부 판단
- PM은 발생 이슈를 체크하고 누가 확인해야 하는지 연결하며, 반영 여부에 대해 일부 판단을 가져갈 수 있음
- 모든 이슈를 PM이 최종 판단하는 구조는 아님

따라서 기존의 **“결정권자 부재”라는 표현은 현재 정보 기준으로는 과도하다.**

보다 정확한 표현:

> **이슈 유형별 판단 주체와 PM이 판단할 수 있는 범위가 명확하게 문서화되어 있지 않아, 실제 운영에서는 판단이 필요한 순간 역할 경계가 모호해질 수 있다.**

즉, 문제를 “팀장들이 수동적이다”로 정의하면 안 된다.

## 5. 22시 이후 대기 문제에 대한 면담 결과

이 부분은 사용자의 핵심 개선 과제에서 제외한다.

리드 설명:

- 22시까지는 필요한 빌드 대응을 위해 작업하는 시간으로 정해져 있음.
- 22시 이후 할 일이 없는 팀원이 계속 남아 있는지는 해당 팀의 운영 문제임.
- PM이 각 팀원의 귀가 여부를 관리할 필요가 없음.
- 팀장들이 자신의 팀에 대해 필요한 작업이 남아 있는지 판단하고 관리해야 함.
- PM은 주요 이슈가 있고 확인이 필요한 사람이 있는 경우 그 상황을 운영하면 됨.

따라서 기존 자료에서 22시를 PM의 “대기 인원 결정/해제 Decision Point”로 정의했던 부분은 삭제하거나 범위를 축소해야 한다.

### 최종 R&R 해석

PM:
- 빌드 일정 관리
- 필요한 빌드 요청
- 주요 이슈 확인
- 확인이 필요한 담당자 연결
- 이슈 현황 공유

각 팀/리드:
- 담당 영역 확인
- 담당 업무의 완성도 판단
- 팀원의 대응 필요 여부 판단
- 팀 내부 운영 및 잔류 여부 관리

PM이 팀원의 근무 종료 여부를 지시하는 구조는 만들지 않는다.

## 6. 현재 중간점검 운영에 대한 리드의 핵심 설명

현재 운영은 다음과 같이 이해하는 것이 정확하다.

1. PM이 계획에 따라 필요한 빌드를 요청한다.
2. 각 팀에서 필요한 부분을 확인한다.
3. Block처럼 검증 자체를 막는 이슈는 우선 대응한다.
4. 그 외 이슈는 담당 리드/팀에서 중요도와 목적에 따라 판단한다.
5. 중간점검은 완성 상태를 확정하는 절차가 아니라 현재 개발 진행도를 확인하는 절차다.
6. 마감 단계가 가까워지면 그때는 변경 통제 및 Branch 관리가 필요해진다.

따라서 현재 중간점검과 향후 마감 운영을 하나의 프로세스로 묶기보다 **목적이 다른 두 단계로 분리해서 보는 것이 필요하다.**

## 7. 기존 제안 중 유지할 것 / 수정할 것 / 보류할 것

### 유지

- 검증 범위/검증 상태/검증 역할이라는 문제 구조
- PM과 각 팀의 역할 분리 필요성
- PM이 직접 모든 빌드를 QA하는 구조를 피하고 각 팀 확인을 요청하는 방향
- 이슈를 단순히 존재 여부가 아니라 대응 필요성 기준으로 보는 관점
- 실제 현상을 Fact와 Hypothesis로 분리
- 변경 이력과 이슈 발생 시점을 비교하여 원인을 확인하는 방식
- 향후 마감 단계에서 Branch/변경 통제 필요성을 검토

### 수정

**중간점검의 목적**
- 기존: 안정화된 특정 상태를 검증
- 수정: 개발 진행도를 확인하고 빠진 요소를 발견하는 Progress Check

**R&R**
- 기존: 팀장/AD가 당일 대응/종료를 최종 결정하는 구조를 강하게 제안
- 수정: 이슈 유형에 따라 PM/리드/담당자가 판단하는 범위를 구분하고 문서화

**22시 운영**
- 기존: PM이 Decision Point에서 대기 인원을 결정
- 수정: PM의 운영 범위에서 제외. 각 팀의 팀 운영 영역으로 본다.

### 보류

**중간점검 안정화 Branch Pilot**
- 현재 프로젝트 단계에서는 리드가 불필요한 공수로 판단.
- 향후 리소스 마감/개발 마감 시점에서 실제 Branch 전략을 다시 설계한다.

## 8. 이번 면담에서 새롭게 생긴 개선 과제

Branch보다 현재 더 직접적인 후속 과제는 **리소스 구조와 변경 관리에 대한 PM의 이해도 확보**다.

리드는 향후 다음과 같은 내용을 PM이 이해할 필요가 있다고 설명했다.

- 리소스가 어떤 Chunk 단위로 구성되는지
- 각 Chunk에 어떤 리소스가 들어가는지
- 리소스가 어떤 구조로 연결되는지
- 어떤 리소스 변경이 마감에 영향을 줄 수 있는지
- 어떤 것은 Dev에 반영해도 되는지/안 되는지 판단할 수 있는 구조 이해
- 클라이언트 데이터와 향후 서버 데이터가 어떻게 구분될지
- 향후 리소스 폴더/구조 정리가 필요한 부분

이는 PM이 소스코드를 직접 이해해야 한다는 의미가 아니라, **리소스가 제작되고 연결되는 구조를 이해하여 변경 영향도를 판단할 수 있는 수준의 도메인 이해**가 필요하다는 의미로 해석한다.

리드가 관련 작업/공유 자리에 참여하여 이해도를 높이는 것을 권장했다.

## 9. 면담 후 최종 문제 정의

현재 단계에서는 문제를 다음과 같이 재정의한다.

> **Dev Build 중간점검은 개발 진행도를 확인하기 위한 절차인데, 중간점검의 목적과 마감 단계의 목적이 혼재될 경우 검증 범위와 이슈 대응 기준을 동일한 기준으로 해석할 수 있다. 따라서 현재 중간점검에서는 진행도 확인과 Block 대응의 기준을 명확히 하고, 실제 마감 단계에서는 별도의 변경 통제/Branch 전략을 적용하는 식으로 목적을 분리할 필요가 있다.**

추가적으로:

> **이슈 대응 판단의 주체가 존재하더라도 이슈 유형별 판단 범위와 R&R이 명시적으로 정리되어 있지 않으면 PM이 판단을 과도하게 떠안거나 반대로 판단 요청이 지연될 수 있으므로, 판단 기준과 역할 경계를 문서화할 필요가 있다.**

## 11. 현재 결론

이번 면담 결과, 기존에 생각했던 **“중간점검용 안정화 Branch Pilot”은 현재 단계에서는 진행하지 않는다.**

가장 중요한 학습은 다음이다.

1. 문제를 해결하기 전에 해당 프로세스의 **실제 목적**을 먼저 확인해야 한다.
2. 중간점검과 마감 검증은 목적이 다르므로 같은 운영 기준을 적용하면 안 된다.
3. Branch는 문제의 목적에 맞는 시점에 적용해야 하며, 현재는 마감 단계가 더 적절한 후보이다.
4. 의사결정 공백은 “팀장 수동성”으로 해석하지 않고, 이슈 유형별 판단 주체와 범위를 명확히 하는 문제로 다룬다.
5. PM의 역할은 운영과 정보 정리/연결에 두고, 각 팀의 내부 인력 운영은 각 팀이 책임진다.
6. 이번 면담을 통해 문제 제안 자체보다 **프로세스 목적과 조직의 실제 운영 의도를 확인하고 제안을 수정하는 과정**이 중요한 Iteration으로 기록된다.

## 12. 포트폴리오용으로 나중에 전환할 때의 핵심 스토리

현재 단계에서 “Branch를 도입했다”는 성과로 만들지 않는다.

오히려 다음 흐름이 정확하다.

> **문제 발견 → 초기 가설 수립 → 운영 개선 제안 → 리드 피드백 → 프로세스 목적 재확인 → 기존 제안 수정 → 실제 프로젝트 단계에 맞는 개선 과제로 재정의**

특히 좋은 학습 포인트:

> **“개발 중인 빌드에서 발생하는 불안정성을 모두 없애는 것이 정답은 아니었다. 중간점검의 목적이 완성도 검증이 아니라 진행도 확인이라면, 불안정성을 감수하되 Block 이슈만 우선 대응하는 것이 현재 단계에 더 적합했다. 대신 실제 마감 단계에서는 변경 통제와 Branch 전략이 필요하므로 문제를 단계별로 분리했다.”**
