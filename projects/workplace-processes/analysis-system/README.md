# 업무 문제 분석 시스템

> 목적: 업무 중 발생하는 문제를 개인의 감정이나 단편적인 현상으로 판단하지 않고, **육하원칙(언제/어디서/무엇을/누가/어떻게/왜)**을 기반으로 사실을 구조화한 뒤 원인·영향·대안·검증까지 연결하는 재사용 가능한 문제 해결 시스템.

## 1. 시스템의 기본 원칙

1. **사실과 해석을 분리한다.**
2. **문제와 증상을 구분한다.**
3. **사람을 원인으로 단정하지 않고 프로세스·조건·R&R을 먼저 확인한다.**
4. **원인을 추정하지 말고 증거와 변경 이력을 확인한다.**
5. **해결책보다 먼저 문제를 정확하게 정의한다.**
6. **하나의 해결책만 주장하지 않고 대안을 비교한다.**
7. **제안 / 합의 / 실제 적용을 구분한다.**
8. **적용 후 결과를 측정하고, 재발하면 분석을 다시 시작한다.**

## 2. 전체 분석 흐름

`사건 기록 → 6W1H → 문제 정의 → 영향 분석 → 원인 분석 → 대안 비교 → 의사결정 → 실행 → 검증 → 재발 분석`

### Phase 1. 사건 기록

발생한 내용을 가능한 한 원문에 가깝게 남긴다.

- 날짜 / 시간
- 관련 대화
- 빌드·배포·변경 시점
- 오류·현상
- 관련자
- 당시 확인된 사실

### Phase 2. 6W1H 구조화

| 질문 | 확인할 내용 |
|---|---|
| 언제 | 최초 발생, 재발, 수정, 검증, 변경 시점 |
| 어디서 | Dev/QA/Live, 특정 빌드, 특정 기능, 특정 단계 |
| 무엇을 | 발생한 현상, 변경된 대상, 영향 받은 기능 |
| 누가 | 발견자, 담당자, 승인자, 의사결정자 |
| 어떻게 | 어떤 조건·순서·행동에서 발생했는지 |
| 왜 | 직접 원인, 근본 원인, 구조적 원인 |

### Phase 3. 문제 정의

다음 세 가지를 분리한다.

- **증상:** 눈앞에서 발생한 현상
- **문제:** 운영상 발생하는 손실 또는 통제 실패
- **핵심 문제:** 반복을 가능하게 만드는 구조적 원인

예:

> 증상: 이전에 수정한 이슈가 다시 발생함
>
> 문제: 검증 완료 상태가 이후 개발 변경으로 유지되지 않음
>
> 핵심 문제 후보: Dev 브랜치의 변경 범위와 중간점검 검증 범위를 분리하지 않음

단, 마지막 항목은 가설이며 변경 이력 확인 전까지 확정하지 않는다.

### Phase 4. 원인 분석

원인을 최소 3개 층위로 본다.

1. **직접 원인:** 바로 현상을 만든 기술적/운영적 조건
2. **프로세스 원인:** 왜 그 조건을 사전에 통제하지 못했는가
3. **구조적 원인:** 같은 문제가 반복될 수밖에 없는 환경·R&R·의사결정 구조는 무엇인가

필요하면 5 Why, Fishbone, 변경 이력 비교를 사용한다.

### Phase 5. 대안 비교

각 대안의 효과뿐 아니라 공수와 운영 복잡도까지 비교한다.

| 대안 | 기대효과 | 추가 공수 | 리스크 | 적용 난이도 |
|---|---|---|---|---|
| 현행 유지 | 낮음 | 낮음 | 재발 지속 가능 | 낮음 |
| 부분 개선 | 중간 | 중간 | 일부 문제 잔존 | 중간 |
| 구조 변경 | 높음 | 높음 | 초기 정착 비용 | 높음 |

### Phase 6. 의사결정

반드시 다음을 기록한다.

- 누가 결정하는가
- 무엇을 결정하는가
- 결정 기준은 무엇인가
- 언제까지 결정하는가
- 결정되지 않을 경우의 fallback은 무엇인가

### Phase 7. 실행

**제안 → 합의 → 실제 적용**을 구분해서 기록한다.

### Phase 8. 검증

개선 효과를 숫자 또는 관찰 가능한 지표로 확인한다.

예:
- 재발 이슈 수
- 추가 빌드 수
- 재검증 횟수
- 대응 인원
- 22시 이후 잔류 인원
- 평균 종료 시간
- PM 직접 QA 건수
- 동일 원인 재발률

### Phase 9. 재발 분석

문제가 다시 발생하면 기존 해결책을 실패로 단정하지 말고 다음을 확인한다.

- 해결책이 실제 적용되었는가?
- 적용 범위가 충분했는가?
- 새로운 변경이 기존 조건을 무효화했는가?
- 문제 정의가 잘못되었는가?
- 원인을 증상 수준에서만 해결한 것은 아닌가?

## 3. 이번 Dev Build 사례에 적용하는 방식

현재 Dev Build 사례는 다음과 같이 분석한다.

`중간점검 운영 문제`
→ 빌드 일정/R&R/대기 기준 개선
→ 운영 중 새로운 문제 발견
→ `Dev의 지속적인 변경으로 기존 검증 상태가 흔들리는 문제`
→ 6W1H 기록
→ 실제 변경 이력 확인
→ 브랜치 분리 필요성 가설 검증
→ 제한적 Pilot 여부 결정
→ 결과 측정

중요한 점은 **'브랜치를 따자'를 결론으로 먼저 정하지 않는 것**이다.

현재 가설은:

> 중간점검에서 검증 완료한 상태를 Dev의 후속 변경으로부터 보호할 필요가 있으며, 이를 위해 별도 안정화 브랜치 또는 다른 변경 통제 방식이 더 효율적인지 검증한다.
