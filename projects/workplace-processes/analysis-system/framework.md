# B. DEFINE — 문제 정의

## 증상
무슨 일이 발생했는가?

## 운영 문제
이 현상이 업무에 어떤 손실/혼란/재작업을 만들었는가?

## 핵심 문제
반복을 가능하게 만든 구조는 무엇인가?

## 해결해야 할 범위
이번 문제에서 실제로 통제해야 할 범위는 어디까지인가?

---

# C. ANALYZE — 원인 분석

## 1. 직접 원인
현상을 바로 발생시킨 조건.

## 2. 5 Why
1. 왜 발생했는가?
2. 왜 그 상태가 만들어졌는가?
3. 왜 사전에 발견/통제하지 못했는가?
4. 왜 현재 프로세스에서는 그것이 가능했는가?
5. 어떤 구조를 바꾸어야 반복 가능성이 낮아지는가?

## 3. 변경 이력 확인
특히 Dev Build/배포 문제에서는 다음 순서로 확인한다.

`정상 확인 시점 → 이후 변경 → 다음 빌드 → 문제 재현 시점`

인과관계를 주장하기 전에 commit/change/build 정보를 확인한다.

# G. ITERATE — 재발/확장

문제가 재발하면 아래 순서로 다시 분석한다.

`기존 해결책 → 실제 적용 여부 → 적용 범위 → 새로운 변경 → 새로운 조건 → 원인 재평가`

기존 해결책을 무조건 유지하거나 무조건 폐기하지 않는다.

# 최종 출력 형식

모든 문제 분석은 최종적으로 다음 구조로 축적한다.

```text
[사건]
↓
[6W1H 사실 정리]
↓
[증상 / 문제 / 핵심 문제]
↓
[원인 가설]
↓
[근거 확인]
↓
[대안 비교]
↓
[의사결정]
↓
[실행]
↓
[결과 측정]
↓
[재발 여부]
↓
[다음 Iteration]
```

이 기록은 나중에 포트폴리오용 `Problem → Action → Iteration → Result`로 변환한다. 단, 원본 기록은 삭제하거나 지나치게 압축하지 않는다.
